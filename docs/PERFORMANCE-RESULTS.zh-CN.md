# 性能测量结果

本文件记录 [性能与资源设计](PERFORMANCE.zh-CN.md) 要求测量的项目里，**哪些已经在这台
主机上测到了、数字是多少、用什么命令得到的**，以及**哪些必须上真实设备才能测、因此现在
一个数字都没有**。

本文件不含任何推测值。每个数字旁边都有产生它的命令，可以在同一台主机上重跑。
**没有从一个数字推算另一个数字**：64 台设备的回复大小不代表 1 台设备在多标签页下的
负载，静态资源字节数不代表首屏时间，主机上的 ucode 耗时不代表路由器上的 CPU。

## 环境

一次测量的数字离开环境就没有意义，所以先记录环境。

| 项 | 值 |
| --- | --- |
| 主机 | macOS 27.0（Darwin 27.0.0，arm64，Apple M4，10 核） |
| 解释器 | `/Users/tanzz/.local/opt/ucode-host/bin/ucode`，由 `jow-/ucode` 自行构建 |
| ucode 源码 | `/tmp/ucode-src`，commit `4a28662538275b67a0bcf11de25c365c1ec7a99d`（2026-10-19，`master`），字节码版本 `0x02` |
| node | v24.13.0 |
| bash | GNU bash 3.2.57(1)-release (arm64-apple-darwin26) |
| gzip | Apple gzip 487.0.1 |
| 网络 | 测量不需要网络，三个套件都没有网络访问 |

两条必须记住的前提：

1. **ucode 不是 CI 钉住的那个版本。** CI 构建的是标签 `v0.0.20250529`，本次是
   `master` 上的 `4a28662`。`sprintf('%J')` 的序列化细节（例如 null 字段是否省略）由
   解释器决定，换一个解释器字节数可能有小幅差异。要复现本文的数字，请使用上表的 commit。
2. **以上全部是主机数字。** 没有路由器、没有音箱、没有浏览器、没有真实 rpcd/ubus。
   主机上的 ucode 与路由器上的同一个 ucode 在算法上等价，但**执行时间**不可比。

## 1. 静态资源首屏字节

页面必须取回的文件：`htdocs/luci-static/resources/` 下全部内容（安装到
`/www/luci-static/resources/`），加上 LuCI 解析视图时要读的 menu 与 acl JSON。

命令：

```sh
bash tests/performance/measure-payload.sh
```

测量日期 2026-10-22 的结果（高级引擎参数接入后于同日重测）：

| 文件 | 未压缩字节 | `gzip -9` 字节 | 上限 |
| --- | ---: | ---: | ---: |
| `.../resources/view/airconnect-manager/overview.js` | 30,327 | 9,069 | 49,152 |
| `.../resources/airconnect-manager/manager.css` | 9,388 | 2,172 | 24,576 |
| `.../resources/airconnect-manager/rules.js` | 7,437 | 3,051 | 12,288 |
| `root/usr/share/luci/menu.d/luci-app-airconnect-manager.json` | 265 | 172 | 2,048 |
| `root/usr/share/rpcd/acl.d/luci-app-airconnect-manager.json` | 358 | 182 | 2,048 |
| **合计（5 个文件）** | **47,775**（46.7 KiB） | **14,646**（14.3 KiB） | 65,536 |

`gzip -9` 从标准输入读取，因此归档里不写入文件名与 mtime，同样的内容永远得到同样的
字节数；直接按文件名压缩会把检出时间写进头部，数字就不可复现了。

这 5 个文件是本包的**全部**静态贡献。**没有测量**：LuCI 核心自身（`luci.js`、form
框架、主题）的字节数、请求个数、HTTP 头、TLS/压缩协商、缓存命中率——那些不在本包内，
也不由本包控制。所以上表是"本包新增了多少"，不是"首屏总共要多少"。

### 预算与余量

| 上限 | 依据 | 余量 |
| --- | --- | --- |
| 合计 65,536 B | 实测 47,775 B | +37 % |
| 合计 gzip 32,768 B | 实测 14,646 B | +124 % |
| `overview.js` 49,152 B | 实测 30,327 B | +62 % |
| `manager.css` 24,576 B | 实测 9,388 B | +162 % |
| `rules.js` 12,288 B | 实测 7,437 B | +65 % |
| menu/acl 各 2,048 B | 实测 265 / 358 B | 约 6× |
| 任何其他文件 32,768 B | 默认上限 | — |

余量刻意放大到接近"翻倍"：一个日常编辑就触发的上限，只会教所有人改上限而不是看数字。
这些上限要拦的是**事故**——误提交的 source map、以 data URI 内联的字体、被拷进来的
框架——它们都远大于一次正常改动。

默认单文件上限的意义是：新增文件会自动被合计覆盖，不需要同时改脚本；它可以存在，
只是不能很大。

### 断言确实会失败（已演练）

在 `manager.css` 末尾临时追加 30,000 字节 base64（模拟一个误内联的字体），重跑：

```
manager.css  39515  2389  24576  OVER
total (5 files)  70826  12530  65536
FAIL  total payload 70826 bytes exceeds the 65536 byte cap by 5290
FAILED  2 budget violation(s)
exit=1
```

随后用 `git checkout --` 还原，重跑恢复 `exit=0`。**被测文件当前未被改动**。

## 2. status / logs 回复字节

驱动的对象是**真实的** rpcd 插件
（`packages/airconnect-manager/files/usr/share/rpcd/ucode/airconnect-manager`），
通过 `loadfile()` 加沙箱根目录、以及 `tests/state/stubs.uc` 的假 `uci`/`ubus` 模块运行。
这套假模块与 `tests/state/plugin.uc` **共用同一份实现**，不是另写一份：否则这里的数字
可能来自一个比功能套件更宽容的后端。

命令：

```sh
bash tests/performance/measure-status.sh
```

被测量的量是 `length(sprintf('%J', reply))`，也就是 rpcd 会把一条回复放到线上的 JSON
字节数。它**不是** HTTP 载荷（rpcd/LuCI 还会加上外层封装和响应头），也不是字符数
（ucode 的 `length()` 按字节计）。设备字段按 `state.uc` 允许的上限构造：
UDN 255、AirPlay 名称 63、型号与厂商各 128、地址 45。用短演示字符串测出来的数字在真实
局域网里不成立，所以不用短字符串。

### status

| 设备数 | JSON 字节 | 上限 | 说明 |
| ---: | ---: | ---: | --- |
| 1 | 792 | 4,096 | 家用场景的实际情形 |
| 8 | 4,607 | 65,536 | |
| 32 | 17,707 | 65,536 | |
| 64 | 35,167 | 65,536 | 后端硬上限，最坏情形 |
| 128 个候选 | 35,167 | 65,536 | 实际只返回 64 条 |

64 台设备的数字是本套件**最有价值的一次发现**：脚本初稿里我按经验写成 32 KiB 上限，
实测是 35,167 字节，断言当场失败。上限因此改为 64 KiB（+86 %），而代码里保留的注释说明
了"这个上限描述的是边界，不是使用量"——家用局域网没有 64 台音箱，描述真实使用的是 792
字节那一行。

128 个候选只返回 64 条，并且**回复字节与正好 64 条时完全相同**：这说明
`state.uc` 的 `MAX_DEVICES = 64` 是一个真正生效的边界，不只是注释。
（若上限只写在文档里，128 个候选会得到 128 条或崩溃，两者都会让这条断言失败。）

### logs

| 输入 | 输出 | JSON 字节 | 上限 |
| --- | --- | ---: | ---: |
| 200 条写实日志行（原始 23,981 B） | 200 行 | 24,617 | 163,840 |
| 5,000 行 | 200 行，`truncated:true`，保留最新（`event 4999`） | 12,326 | 163,840 |
| 200 × 4,000 字节行 | 16 行，每行被截到 512 字节，文本 8,207 B | 8,290 | 163,840 |
| 200 行 × 512 字节全是反斜杠 | 127 行，文本 65,150 B | **130,590** | 163,840 |
| 无日志文件 | 0 行 | 36 | — |

两处上限都被**证明在执行**，不是只在文档里：5,000 行进、200 行出；单行 4,000 字节进、
512 字节出；文本总量不超过 64 KiB。

#### 一个必须写下来的坑：上限约束的是文本，不是 JSON

后端的两个上限（200 行、64 KiB）约束的是**日志文本**。rpcd 放到线上的 JSON 更大，大多少
取决于日志内容：一个引号或一个反斜杠在序列化时变成两个字节。

| 65,150 字节的文本，内容是 | JSON 结果 | 倍数 |
| --- | ---: | ---: |
| ASCII（`x`、2/3/4 字节 UTF-8 同此） | 65,566 | 1.00 |
| 双引号 `"` | 130,590 | 2.00 |
| 反斜杠 `\` | 130,590 | 2.00 |

`logs` 的预算因此是 **160 KiB**（163,840 字节，余量 33,250 字节），不是初稿按"1.5 倍差不多"猜的
96 KiB。96 KiB 会被一个每行都引用一个路径的引擎日志当场打破——这也不假设：这条测试就是
这么写的，加上去之后旧的 98,304 上限立刻失败。上限现在的依据是"2 倍整的转义（131,072）
+ `lines`/`truncated` 外层 + 少量余量"，并且测试里还有一条
`bytes <= 2 * 65536 + 4096` 的断言把这个推导本身钉住。

### 每次调用的子进程数

回复大小不说明路由器要花多少代价产生它。主机上唯一能观察到的这部分代价是进程创建次数，
因为 600 MHz 路由器上一次 `fork+exec` 与这份 JSON 一样贵。

| 调用 | 子进程 | 说明 |
| --- | ---: | --- |
| `status` | 1 | `detectConflicts()` 每次都要跑一次 `ps w` |
| `logs`（有日志文件） | 0 | 直接读文件；只有没有日志文件时才走 `logread` |

测量方式是在沙箱里放一个会给自己记数的假 `ps`，读完文件大小即为调用次数。这条断言要求
正好等于 1：0 说明假 `ps` 被绕过、计数什么也没证明，2 以上说明 `status` 又多了别的
外部命令。

### 两次"先测再定"把初稿的上限推翻了

任务要求上限必须从实测导出，不能凭猜测。这件事在本套件里发生了两次，都保留在这里：

| 上限 | 初稿（按经验） | 实测 | 最终 | 初稿为什么会错 |
| --- | ---: | ---: | ---: | --- |
| `status` 64 台设备 | 32,768 | 35,167 | 65,536 | 低估了每台设备在字段上限下的字节数 |
| `logs` 最坏情形 | 98,304 | 130,590 | 163,840 | 只看"文本有 64 KiB 上限"，忘了 JSON 转义会翻倍 |

两次都是**断言先失败、然后改上限**，不是反过来。如果当初把上限写得宽松到不会失败，这两个
数字就不会被发现，上限也就只是装饰。

## 3. 轮询契约

`docs/PERFORMANCE.zh-CN.md` 与 `docs/ARCHITECTURE.zh-CN.md` 用散文承诺了四件事：10 秒
轮询、`document.hidden` 时暂停、同类请求最多一个在途、连续失败退避到 60 秒；另有一条
"状态刷新不重绘表单"。这五条决定"多开一个标签页是否让路由器的 RPC 负载翻倍"，此前
没有任何测试执行过它们。

命令：

```sh
node tests/performance/poll-contract.mjs
```

测试加载**未修改的生产视图** `overview.js`（与 `tests/parity/check-frontend.mjs` 相同的
`new Function` 模块垫片），用假的 `rpc`、`uci`、`poll`、`form`、`E`、`document` 驱动它
真正的轮询入口。没有浏览器、没有 LuCI、没有 npm 依赖、没有网络。

| 断言 | 结果 |
| --- | --- |
| 注册的轮询间隔 | 正好 10 秒 = 10,000 ms |
| `document.hidden === true` 时 | 跳过；连续两次都跳过 |
| 重新可见后 | 立即恢复轮询 |
| 有请求在途时 | 第二个刷新被跳过；在途请求结算后恢复 |
| 连续失败的延迟序列 | 10,000 → 20,000 → 40,000 → 60,000 → 60,000 ms |
| 退避未到期时 | 不发请求；到期准时发 |
| 成功一次后 | `failures` 归零，恢复 10 秒 |
| `updateStatus` 对表单写入 | **14 个表单控件，2 次状态更新，0 次写入** |

"不重绘表单"是**在 DOM 垫片上断言**的：垫片记录每个节点的每一次变更，测试在
`render()` 完成后清空记录，再喂三种每个被渲染字段都不同的 status 回复（服务状态、
冲突、扫描、设备事实全变），然后要求那 14 个控件的写入记录、`value`、`checked` 全部
不变。最后还有一条自检：故意改一个控件的 `value`，确认同一套比较能发现它——否则一次
重构可以把这条测试悄悄变成空操作。

### 断言确实会失败（已演练）

| 故意注入的缺陷 | 失败的断言 |
| --- | --- |
| `poll.add(this.pollFn, 10)` 改成 `15` | `the poll interval is exactly 10000 ms: 15000` |
| 去掉 `document.hidden` 判断 | 3 条隐藏相关断言 |
| 去掉 `this.inflight` 判断 | `a second refresh is skipped while one is in flight` |
| 去掉 `Math.min(60000, …)` 上限 | 8 条退避断言（含 80,000 ms 越界） |
| 让 `updateStatus` 写一个 input 的 value | `wrote value,value to #ac-probe-input` |

每次演练后都用 `git checkout --` 还原，`git diff` 确认视图未被改动，重跑恢复
`29 passed; 0 failed`。

### 视图是否被为测试而重构

**没有。** 现有 `overview.js` 的 `refresh()` 已经是一个把决策写在一行里的纯判断
（`document.hidden || this.inflight || Date.now() < this.nextRetry`），在垫片下可以被
完整驱动，因此一行生产代码都不需要改。这一点在这里写明，是因为任务允许"必要时做最小
重构"，而实际情况是不需要。

## 未测量

以下项目**必须**有路由器和音箱才能得到，本文件一个数字都没有。不要从上面任何数字推算
它们。

| 项目 | 为什么测不了 |
| --- | --- |
| 路由器 CPU：空闲 | 没有路由器。主机上的 ucode 耗时与 MIPS/ARM 路由器不可比 |
| 路由器 CPU：一条播放流 | 没有音箱，也没有可播放的音源 |
| 路由器 CPU：多条并发流 | 同上；并且文档要求不默认增开并发流 |
| 路由器 CPU：FLAC 转码 | 同上。上游说明 FLAC 更耗 CPU，这一点只能用真实播放验证 |
| 路由器 CPU：扫描期间 | 发现需要在真实接口上发组播；主机只有假 discovery |
| `airupnp` / `aircast` 的 RSS | 没有运行中的引擎进程 |
| `airupnp` / `aircast` 的 VSZ | 同上。且 VSZ 不是 RSS，不能互相替代 |
| 路由器内存峰值 | 需要 RSS 在"播放/转码中"的采样，不是空闲快照 |
| 网络流量与突发 | 需要真实接口抓包；主机上的字节数只是 ubus 载荷 |
| 播放中断 | 需要正在播放的音箱；任何 RPC 开销的最终判据都是它 |
| 浏览器长任务 | 需要真实浏览器跑真实 LuCI；`dev/` 预览与 node 垫片都不是浏览器 |
| 首屏渲染时间 / LCP / TBT | 同上 |
| 多标签页下的实际请求频率 | 需要真实浏览器里开多个标签；本套件只证明了单实例的决策逻辑 |
| 真实 LuCI 下的表单行为 | 垫片实现了本视图用到的 LuCI 子集，不是真 LuCI |
| ubus blob / HTTP 外层开销 | rpcd 与 LuCI 加在 JSON 外面的部分，主机无法观察 |
| 请求频率对发现的影响 | 文档要求"UI 状态请求不触发媒体处理"，这需要真实引擎观察 |

## 从已测数字能得出、但不能外推的结论

以下是**算术**，不是测量，标注在此以免被误读：

- 1 台设备、1 个可见标签页、每 10 秒一次 status = 792 B / 10 s ≈ 79 B/s 的 ubus JSON。
  这是载荷字节，**不含** ubus blob 与 HTTP 外层，因此实际线上字节更多，具体多多少未测。
- 页面隐藏时不发请求，所以"关闭/隐藏不新增周期性管理请求"这一条从**决策逻辑**上成立
  （已有断言）；它在真实浏览器里是否成立取决于浏览器对 `document.hidden` 的实现，
  未测。
- 这个算术**不能**乘上标签页数、设备数或时间换算成"每天多少流量"，也不能换算成 CPU：
  每一项都缺一个未测的系数。

## 复现

```sh
# 三个套件单独运行
bash tests/performance/measure-payload.sh
bash tests/performance/measure-status.sh
node tests/performance/poll-contract.mjs

# 与其余全部套件一起运行（当前 14 个套件）
bash scripts/run-tests.sh
```

三个套件都只看退出码：预算或断言不成立时退出码为 1，运行环境有问题（找不到 ucode、
包目录不存在）时为 2。

# 新版管理界面需求

状态：界面与后端已按本文实现，并有主机测试；尚未在真实 LuCI、rpcd/UCI 和路由器上验证，也未发布。

## 设计方向

用户确认：简洁易用、系统设置式，参考 shadcn 风格。继续使用 LuCI 的登录、导航、权限和部署方式。shadcn 在此是视觉与交互参考；现有 LuCI 页面不是 React 项目，不为套用组件库强制引入 React 服务端或 Node 常驻进程。

使用克制的中性色、清晰分隔、统一输入控件与按钮、可见焦点、少量语义状态色。样式仅作用于 AirConnect 页面，不覆盖全局 LuCI 控件。优先兼容明暗主题及手机窄屏；正式视觉 token 随界面实现验证。

## 页面结构

### 音箱

默认入口展示音箱列表和服务摘要。显示 AirPlay 显示名称、设备原名称、型号、地址、协议、最后发现时间和桥接状态。详细信息展开后展示厂商、UDN/设备标识和探测时间；不可获取的数据写“未提供”，不能编造。

常用操作：启用/停用桥接、修改 AirPlay 显示名称、音量上限（仅适用引擎显示）、恢复继承值。UDN 用作 UPnP 设备关联键，地址只作当前发现信息。不要把个人 IP、设备名或 UDN 写进发布包。

“修改 AirPlay 名称”只修改虚拟接收器名称，不修改原厂 App 的设备名称。提供恢复默认名称、清空覆盖值、重名警告；前后端校验 UTF-8 字节长度、控制字符和 XML 转义。具体引擎字段与边界以能力审计为准。

### 设置

基础区：服务开关、绑定局域网接口、UPnP/Chromecast 引擎、全局默认值。设备设置可覆盖全局设置，并显示继承关系。

高级区：音频格式、延迟与缓冲、设备过滤和协议兼容参数。参数要注明适用引擎，优先保留上游默认，不宣称“越低延迟越好”。

### 诊断

服务运行、设备发现、AirPlay 广播、实际播放分别展示，不相互推断。四者的数据源各不相同：

| 状态 | 数据源 | 何时已知 |
| --- | --- | --- |
| 服务运行 | procd 的 `service list` | ubus 能回答时；问不到显示未知 |
| 设备发现 | SSDP 发现缓存（24 小时） | 有一次成功的扫描；否则未知 |
| AirPlay 广播 | mDNS 观测 `_raop._tcp`（5 分钟） | 有一次完成的观测；失败、超时、过期或接口使前缀不可推导时未知 |
| 实际播放 | 上游没有文档化接口 | 永远未知 |

广播按引擎分行（UPnP / Chromecast），因为引擎在 TXT 记录里用 `am=` 标记区分；
每行展示值与观测时间。设备卡片上另有一个广播徽章，与“已发现”徽章并列而不是合并。

“未测量”必须渲染为未知，不得渲染为肯定，也不得因为另一个状态为真而变成肯定：
服务在跑、音箱被发现都不代表在广播；广播为真也不代表在播放。已知的否定（扫描完成
但没找到）要写成明确的否定并附观测时间，与未知区分开。

提供有超时和防重复点击的重新扫描、受限日志查看、服务重启。扫描同时产生发现与广播
两种观测；状态轮询只读缓存，不发起 mDNS。扫描空结果提示检查音箱在线、DLNA 和局域网；
不自动关闭隔离、防火墙或改 DNS。诊断导出先展示内容范围，避免泄露不必要的局域网信息。

## 保存流程

更改先留在表单；“保存并应用”明确提示会短暂断开 AirPlay。只有成功生成配置并完成服务应用后才能显示成功。失败保留最后有效配置并呈现原因。待保存、应用中、失败、空列表、探测超时、设备离线和部分引擎运行均需明确界面。

## 验收

- 桌面与手机可操作，无横向溢出；键盘可完成名称/音量修改。
- 多设备名称/音量互不影响，中文及特殊字符安全保存。
- 设置重启和软件包升级后保留；无效配置不会替换运行配置。
- 保存反馈与实际 UCI/XML/进程一致；不能只凭截图确认功能。
- 主题和 CSS 不影响其他 LuCI 页面。
